## 参加者がたどる体験

現行仕様上の表示候補は、参加コードと名前の入力 → ロビー → お題と残り時間 → カメラ → 写真確認 → 送信・判定中 → 合否と得点 → 順位・次問待ち → 最終結果。URLは画面ごとに増やす必要はなく、部屋のサーバー状態で表示を切り替える。画面一覧と状態は[03](../03-ui-frontend.md)を参照。

参加者側で特に扱う状態（仕様案であり、取り込み実装には未実装のものを含む）:

- カメラ許可待ち・拒否・利用不可、撮り直し、画像圧縮失敗。
- 送信中、判定中、合格・不合格・不明、AI/通信の処理失敗。
- 締切、残り提出回数、通信切断、タブ復帰、再読込後の復帰。
- `serverTime` に基づく残り時間。得点と締切の最終決定はAPIの値を表示する。

[公開検証ページ](https://ai-karimono-race.ahwenu.chatgpt.site/verification.html)には、ログイン不要の参加、初回参加から30秒での自動開始、合格イベントと通知、参考写真、Decisions APIへの実画像送信、70接続のデモ負荷などの試験結果が記載されている。これはページの記録を読んだもので、この作業では試験を再実行していない。検証ページ自身も、実AIの少数例とデモ負荷、実機・会場回線の未検証範囲を分けている。

公開画面・検証ページの記述と現行仕様書には差がある。例: Sites上のホスト用部屋作成（ADR-0001ではPlugin Extensions）、画面名（ADR-0007ではカリモノ）、30秒自動開始（01ではホスト開始）、参考写真（01では完成版の範囲）、画像縮小の上限（03では1280px/2MiB、実装では960px/1MiB）。下記のコード確認でも同じ差を確認した。

## 取り込まれた実装の現在地

`apps/web/app.js` が参加者画面とブラウザ用ホスト画面を同じファイルで組み立て、`apps/web/live-camera.js` が参加者のカメラ表示と撮影を担う。Sites向け配信・APIは `apps/cloud/` にあり、`apps/server/` はローカル開発用のサーバー。コードの配置と取り込み範囲は[10](../10-demo-import.md)に記録されている。

| 項目 | コードで確認した現状 | 現行仕様との関係 |
| --- | --- | --- |
| 画面 | `/rooms/:id/join` で名前と任意の自己紹介を登録し、同じ画面にカメラ、お題、結果、順位を表示する。`/rooms/:id/host` と部屋作成もSites内にある | 参加者のブラウザ利用とは一致。ホストの配置はADR-0001と異なる |
| カメラ | 許可は明示操作。映像を中央で切り出し、長辺960px以下・1MiB以下のJPEGへ変換し、シャッター後すぐ送信する。非対応端末は写真選択へ進む | 03の「送信前プレビュー・撮り直し」「長辺1280px・2MiB」と異なる。即送信は議事録の速い判定体験に近い |
| 送信・復帰 | 新規送信にrequestIdを付ける。応答を失った時は自動再送せず、同じ写真・キーでの明示再試行。状態取得は画面表示中、処理中はおおむね0.8〜1.4秒、待機中は1.5〜2.5秒 | 04のIdempotency-Keyヘッダー、GETのスキーマ、2秒ポーリング案とは契約が異なる |
| セッション | 参加者トークンとIDを部屋別のlocalStorageに保持し、Bearerで送る。ホストは部屋別HttpOnly Cookie | 04の参加者Secure/HttpOnly Cookie案と異なる |
| ゲーム表示 | 最初の参加から30秒で自動開始し、各ラウンドの撮影受付・判定・合格イベントを表示。合格数と受付時刻から順位を計算する | 01の「ホスト開始・共通3問・10点・同点同順位」案と異なる |
| 演出 | 自分の合格カード、他者のクリア通知、紙吹雪、任意の効果音、動きを減らす設定を実装済み | さがさんメモの希望の一部がすでに入っている |

根拠: `apps/web/app.js` の参加・送信・状態取得・表示、`apps/web/live-camera.js` の撮影、`apps/cloud/lib/cloud-api.ts` のsnapshotとAPIルート。公開検証ページの数値はコード再実行の証拠とは区別する。

読み取り後に `node --test tests/camera.test.mjs tests/camera-app.test.mjs` を実行し、17件が成功した。これは模擬DOMと通信境界を使うテストであり、実機カメラや公開サイトの投稿を検証した結果ではない。

## クリーンアーキテクチャ寄りの境界

| 層 | mae担当が扱うこと | 外部との受け渡し |
| --- | --- | --- |
| 表示 | Akibakoさんの表示部品を画面状態に応じて組み立てる。色だけに頼らず合否・エラーを伝える | 部品のpropsと状態見本は[03](../03-ui-frontend.md) |
| 参加者の操作 | 参加、撮影、再撮影、提出、判定確認、部屋再取得、復帰を一連の操作として管理する | サーバーの採点・締切を端末で複製しない |
| API境界 | 共有DTOとエラーコードを利用し、Cookie、Idempotency-Key、`room.version` を扱う | 契約の正本は[04](../04-api-contract.md)。変更時はAhwenu・さがさんと確認 |
| 端末アダプター | カメラ、JPEG変換・縮小、プレビューURL解放、ポーリングとタブ復帰 | 実機確認が必要。端末時計は採点に使わない |

画面からDB/R2やOpenAIへ直接つながず、`参加者画面 → 操作と状態 → APIクライアント → Sites API` の依存に寄せる。現在は画面・操作・API呼出の多くが `apps/web/app.js` に同居しているため、この依存方向は整理の目標であって実装済みの構造ではない。ホスト拡張は別UIで、同じAPIの管理権限をMCP経由で使う方針だが、取り込まれたコードにはSites内のホスト画面がある。ディレクトリ案と現状の差は[09](../09-repository-structure.md)と[10](../10-demo-import.md)を参照。

## 追加メモと現行仕様の差

| 論点 | 現行文書 | 追加メモでの希望 | 次に必要なこと |
| --- | --- | --- | --- |
| お題の進行 | 共通3問を開始前に準備し、ホストが次へ進める案 | 最初の正解で次のお題を生成・追加 | ゲームルール、API状態、終了条件を関係担当で合わせる。mae担当だけで進行を変更しない |
| 得点 | 合格10点、速さによる加点なしの案 | 順位に応じた特典、FIRST CLEAR演出 | 得点の正本と順位確定時点をサーバー契約で決める。画面の演出は確定値を受けて出す |
| 参加者への通知 | 2秒ポーリングで部屋・順位を更新する案 | 他の人のクリアを知らせたい | 実装には合格イベントとカットイン、既読管理がある。新APIへ移すときはイベントIDと重複表示防止を保持する |
| 演出 | MVPは画面内の合否表示と順位更新 | 紙吹雪、次のお題の登場演出 | 実装には紙吹雪・音・動きの抑制がある。次のお題の演出は未確認 |
| 画面配置 | 参加者はSites、ホストはPlugin Extensions | 古い議事録とさがさんメモに異なる表現 | AcceptedのADR-0001を基準にする。変更なら後継ADRへ |

議事録のMVPの芯は「お題を見てスマホで撮り、すぐにOK/NGと撮影物による結果が分かる」体験。複数のお題やリアルタイムランキングは議事録では追加候補で、現行の01ではMVP案に含まれる。実装の優先順位を決める際は、この差をチームに見せる。

## この先の変更順序

1. 参加者の「見つける→撮る→判定→結果」の体験を保ちつつ、現行のデモAPIをどこまで継続利用するか関係担当で合わせる。ホスト配置・参加認証・得点・お題進行は、mae担当の画面だけで変更できない。
2. 合意した契約に沿って、まず参加者の画面状態と操作、API通信、カメラを境界で分ける。表示部品はAkibakoさんの状態見本を受け、サーバーの確定値を描画する。
3. 変更する画面状態・API契約・ゲームルールは関連仕様とADRに同じ変更で反映する。`apps/cloud`、`apps/server`、`plugin` の変更が必要なら各担当へ受け渡す。
4. モック、自動テスト、実API、実機を区別して確認する。iPhone SafariとAndroid Chromeの実撮影はMVP条件に残る。

## 2026-10-18 参加者画面の追加作業

提供デザイン画像から、現行Sitesの `apps/cloud/app/rooms/[id]/join/` にTypeScript/Reactの参加者画面を追加した。8画面の見本は `apps/cloud/app/design-preview/` で切り替えられる。元画像と現在使う素材の関係は [デザイン共有フォルダ](../design/README.md)、配信境界は [ADR-0012](../adr/0012-participant-typescript-ui.md) を参照する。

型チェック・Sitesビルド・ローカルの画面表示は確認した。実在する部屋での参加から提出まで、公開Sitesへの配備、iPhone/Androidの撮影、100人の同時利用は未確認。上の「この文書作成時点」の記述は元の索引作成時の記録として残し、この追記で追加作業の範囲を区別する。
