## 状態

- **Proposed**：提案中。未検証や合意前の事項。実装済み・採用済みを意味しない。
- **Accepted**：採用する方針。決定の根拠にユーザー指示または実際の合意・検証記録を明記する。実装完了とは別。
- **Rejected**：検討したが不採用。理由を残す。
- **Superseded**：新しいADRに置き換えられた判断。後継へのリンクを残す。

## いつ・誰が更新するか

重要な方針決定、技術検証による採否確定、既存方針の変更時に、作業担当者がコード・仕様と同じ変更でADRを更新する。Codexがその作業を行う場合も同じルールを適用する。定期実行やバックグラウンドの自動更新ではなく、開発作業に連動して更新する。

主な記録担当：UI方針はAkibako さん、モバイル処理はmae さん、ゲーム/DB/保存はさが さん、API/AI/MCPはAhwenu。複数領域の変更は関係担当を記載する。拡張画面は未定（Ahwenu）を維持し、担当確定時に記録する。

## 更新手順

1. 関連する既存ADRと現在の仕様を読む。
2. 新しい論点は次の4桁連番＋英小文字のファイル名で作り、[テンプレート](template.md)を使う。IDは再利用しない。
3. Proposedの検討内容・検証結果は同じファイルへ追記する。採用・不採用が決まったら状態と根拠を更新する。
4. Acceptedの決定そのものを変える場合は新規ADRを作る。新案の採用後に旧ADRをSupersededとし、双方へリンクする。採用前は旧方針が有効。
5. 一覧と各ADRの最終更新日、変更履歴を更新し、Project.mdと関連仕様書を同期する。
6. 変更の説明に関連するADRのIDを添える。秘密値や写真本体は記録しない。

誤字や説明補足は既存ADRへ直接修正できる。決定の意味を変える更新と区別する。ユーザーの新しい指示と既存ADRが矛盾した場合は新しい指示を優先して反映し、その経緯を記録する。
