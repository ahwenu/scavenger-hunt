# ADR-0020: SitesのD1/R2を継続し、待機部屋の参加QRを事前配布する

- 状態：Accepted
- 作成日：2026-10-18
- 最終更新：2026-10-18
- 関係担当：さが さん（保存・ゲーム処理）、Ahwenu（HTTP/AI・拡張接続）、mae さん（参加者画面）。拡張画面の正式担当は未定（Ahwenu）
- 決定の根拠：ユーザーの「新しい変更をプルして、データベースをフロントで使っているものに合わせて」「すでに実装しているものと同じくSitesのもの（D1?）」「QRを事前に作成して配布する機能」の確定指示。Acceptedは採用方針であり、今回の変更の検証・配備完了を意味しない
- 置き換えるADR：[ADR-0016](0016-supabase-game-persistence.md) のSupabaseへの保存移行方針。[ADR-0013](0013-issue1-player-game-contract.md) の初回30秒自動開始は既存の自動開始部屋へ継続し、事前招待部屋の例外を追加する
- 後継ADR：なし

## 背景

参加者画面は同一オリジンの `/api/rooms/:id` を呼び、Cloudは既存のD1とR2を使う。ADR-0016ではSupabaseへ移す方針だったが、移行は実施されず、公開Sites v6もD1/R2で配備されている。最新のユーザー指示は、画面と同じSitesの保存構成で使えるようにすることと、他の人へQRを事前配布できるようにすることだった。

最新main `e35cc05` を取り込み、[ADR-0018](0018-participant-media-audio.md)の参加者音声・効果音と[ADR-0019](0019-participant-root-entry.md)の新しいルート入口を維持して統合する。既存参加URLと今回の事前招待は両方の画面から同じSites APIを使う。コードの統合・commit/pushと、その後のSites/Pluginへの配備は別々の完了として記録する。

従来の部屋は最初の参加から30秒後に第1競技を自動開始する。この挙動のままでは事前に参加した人によって本番前にゲームが始まる。また、MCPのプロセス内だけにホストCookieを持つ方式では、準備と当日の間にMCPが再起動すると同じ部屋を管理できなくなる。

## 決定と範囲

- 部屋・参加者・競技・提出・ヒントの永続化先はSitesの**D1**、写真は既存の非公開**R2**とする。得点と順位は永続した提出記録からサーバーが確定する。Supabaseへの移行・二重書き込み・ブラウザからの直接DBアクセスを追加しない。以前のSupabase指示と未実施の移行計画はADR-0016に残す。
- Sitesの参加者画面、ゲームAPI、Plugin Extensionsのホスト画面は同じ部屋を利用する。既存の `/api/rooms/:id`、参加者Bearer、部屋別HttpOnlyホストCookie、100人・10競技・初合格500点・共通ヒントの契約を維持する。
- `POST /api/rooms` に `autoStart?: boolean` を追加する。省略時は従来どおり `true`。Plugin Extensionsから新規作成する事前招待部屋は `false` を指定してD1へ保存する。`false` の部屋では参加しても開始カウントダウンを作らず、ホストの明示的な開始操作まで待機する。既存の自動開始部屋の動作は変更しない。
- QRは部屋を事前作成した時点で同じ `/rooms/:id/join` の参加URLから生成する。当日に別の部屋やURLを作り直さず、事前登録済み参加者を継続利用する。配布機能は参加URLコピーとQR画像の保存を提供する。外部QRサービスへ参加URLを送らない。
- 配布物・参加URL・参加者向け応答へホストCookie、OpenAIキー、サービス認証秘密を含めない。QRの保存はMCP Apps SDKのホスト機能を使い、未対応ホストでも参加URLを選択してコピーできるようにする。
- 同じ端末・Sites接続先でMCPを再起動しても事前部屋へ戻れるよう、ホスト権限はMCPサーバー側のユーザー状態ディレクトリへ権限0600で保存する。保存した接続元を検証し、別のSites originへ送らない。ローカル状態をGit・共有アーカイブへ入れず、ゲームの正本はD1に保つ。別端末へのホスト権限配布や復旧は本ADRに含めない。
- 人数と順位は既存の定期取得を継続する。状態に `revision`、`live`、`stats.activePlayers` を追加し、D1で永続した版・更新時刻と直近30秒の認証通信の近似人数を使う。厳密なオンライン在席保証とはしない。仕様は[16](../16-supabase-integration.md)にまとめる。

## 代替案と理由

Supabase移行を続ける案は最新のユーザー指示と異なり、既存Sitesで確認しているD1/R2に別の接続・スキーマ・認可の作業を増やす。QRだけ事前生成して当日に別部屋を作る案では、配布済みURLと事前登録済み参加者が一致しない。既存全室の自動開始を廃止する案は既存クライアントの契約を変えるため、部屋ごとの設定を追加する。

## 影響と受け渡し

Sites側で部屋の開始方式とライブ表示用の保存項目を追加し、既存行には互換の既定値を与える。スキーマ変更は追加マイグレーションとし、過去のSQLを書き換えない。参加者画面は開始方式に沿った待機説明とサーバー確定値を表示する。Plugin側は事前招待・QR配布・ローカルの部屋復帰を実装する。SitesとPluginは独立したビルド単位を維持する。

## 検証・見直し条件

既存のD1/R2公開配備と100HTTPクライアントのデモ試験は[12 Sites配備](../12-sites-deployment.md)・[14](../14-issue1-ahwenu-handoff.md)の過去の実績として保持する。今回の新機能の成功やSupabaseの検証には読み替えない。

今回確認する対象は、追加マイグレーション、事前部屋への参加後も未開始であること、ホスト操作での初回開始、既存自動開始部屋との互換、同じ部屋の人数・順位取得、QR画像の読取URL一致、配布物への秘密混入防止、MCP再起動後の復帰である。型チェック・自動試験・ビルドと、ローカル/公開HTTP・拡張ホスト・実機で確認した範囲を別々に記録する。結果は[16](../16-supabase-integration.md)・[08](../08-plugin-extensions.md)へ追記し、未実施の項目は未確認とする。
